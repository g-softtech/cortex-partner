# Cortex Partner Program — Program Structure

**Version:** 1.0

## 1. Partner Journey

The complete Partner journey is:

Visitor  
↓  
Partner Application  
↓  
Application Review  
↓  
Approval  
↓  
Partner Account Setup  
↓  
Partner Agreement Acceptance  
↓  
Partner Resources  
↓  
Opportunity Identification  
↓  
Project Opportunity Submission  
↓  
Cortex Assessment  
↓  
Partner Customer Engagement  
↓  
Project Won  
↓  
Project Kickoff  
↓  
Development  
↓  
Partner Review  
↓  
Change Requests if required  
↓  
Final Approval  
↓  
Delivery  
↓  
Support

## 2. Public Stage

### Partner Application

Route:

`/apply`

Purpose:

Allow a person to apply to join the Partner Program.

The application should be short and should not request detailed customer/project information.

## 3. Onboarding Stage

After approval, the applicant completes account setup and accepts the current Partner Agreement.

Agreement acceptance must record the agreement version and acceptance date/time.

## 4. Resource Stage

Approved Partners receive access to the Partner resources:

- Partner Guide
- Sales Kit
- White-Label Guidelines
- FAQ

Resources are reference materials, not a collection of operational forms.

## 5. Opportunity Stage

When a Partner identifies a potential customer/project, the Partner submits a Project Opportunity.

The purpose is assessment, not full project onboarding.

## 6. Assessment Stage

Cortex reviews the opportunity and provides a Project Assessment/Proposal.

The assessment defines the proposed solution, scope, Partner price, timeline, and relevant conditions.

## 7. Won Stage

Once the Partner wins the project, the project moves to the kickoff stage.

Only then should the system request detailed development information.

## 8. Kickoff Stage

The Partner provides:

- Business information
- Branding
- Logo
- Colours
- Images/media
- Content
- Required pages
- Features
- Integrations
- Domain/hosting information
- Design references
- Project files

## 9. Development Stage

Cortex develops the agreed solution.

Communication should normally flow through the Partner.

## 10. Change Stage

If requirements change, a Change Request is submitted and assessed.

The system must distinguish agreed scope from additional work.

## 11. Delivery Stage

When development is complete, the Partner reviews the project.

The Partner provides Delivery Approval when the project is ready to be delivered to the customer.

## 12. Support Stage

After delivery, Partners can submit technical Support Requests.

A support request may be linked to a specific project.

## 13. Resource vs Workflow Rule

### Resources

Reusable information:

- Partner Guide
- Sales Kit
- White-Label Guidelines
- FAQ

### Workflow

Action-based forms:

- Application
- Project Opportunity
- Project Kickoff
- Change Request
- Delivery Approval
- Support Request

These must be embedded in the appropriate workflow rather than requiring Partners to download and re-upload documents.

## 14. UX Principle

At every stage, the Partner should be able to see what action is required next.

The platform should guide the Partner rather than forcing them to search for forms.
